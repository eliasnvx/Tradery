## 2026-09-30: Economy core
- `Ledger` is pure state + rules (unit-tested): a move checks everything first (amount, fee, locks, funds, overflow, `maxBalance`), then changes both sides. `EconomyService` wraps it with events, saved data, stats, history, log and client sync, in that order, after the ledger move.
- Infinite accounts (`tradery:server`) take part in moves without balances: paying from one creates money, paying into one destroys it. Stats classify every move: emission, burn, cash out/in (coin items).
- `/eco set` is a deposit/withdraw of the difference, so events, log and stats see it.
- Accounts passed in by other mods are resolved by id to this world's account (an `Account` object from an earlier singleplayer session never writes into a stale ledger).
- The world's currency decimals are stored in `tradery:accounts` on first start; a different value in the config later is ignored with a warning.
- Saved data lives on the server storage (`server.getDataStorage()`, files in `data/tradery/`), `DataFixTypes.SAVED_DATA_COMMAND_STORAGE` as the no-op fixer.
- Transaction log: JSON lines written on a daemon thread after commit; `server_start` marker on every start; old files deleted by `log.retentionDays`.

## 2026-09-30: Config
- Own JSON5 reader/writer (`config/Json5`) on Gson's tree; numbers become `BigDecimal`, so money values keep every digit.
- Every field is lenient (a broken value falls back to its default) but always written; `ConfigDiff` compares the file with the decoded config and logs each dropped value or unknown key, so typos are reported instead of silently ignored.
- `server.json5` and `rewards.json5` are written only when missing; `client.json5` is rewritten by the game (HUD toggle), comments are regenerated from the code.

## 2026-09-30: Networking and HUD

## 2026-09-30: Vending
- Trades are menu button clicks (`clickMenuButton`) instead of a custom `VendingBuy` payload: vanilla already checks the click belongs to the player's open menu; the menu checks distance (≤ 8 blocks) and the rate limit (10/s). The only custom C2S is `VendingSavePayload` (the money price); goods, price item and facade are the server's own copies of the sample slots.
- Sample ("ghost") slots copy the cursor stack and never take it; clicks are handled in `clicked()` on both sides, so the client prediction matches.
- The owner edits a draft (data slots + sample slots); "Save" validates (blacklist, facade rules), posts `VendingConfiguredEvent`, applies, and closes every buyer screen of that block when the offer changed — nobody pays a price they didn't see.
- Buyer screens get stock and affordability through two data slots (16-bit, capped at 9999), recomputed in `broadcastChanges`.
- Contents drop in `BlockEntity#preRemoveSideEffects` (removal, not unload), which also closes the menus and updates the vendor index.
- Protection: destroy progress 0 for strangers; creative-mode instant breaking is blocked through Fabric `PlayerBlockBreakEvents.BEFORE` / NeoForge `BreakBlockEvent`; `PushReaction.IMMOVEABLE`; bedrock-level blast resistance.
- Facade: rendered by the block entity renderer with `BlockModelResolver`, squeezed into the base; the blockstate `facade=true` hides the default base model.
- NeoForge GameTest mock players don't have `neoforge:advanced_open_screen`; for such connections menus open the vanilla way (server-side menu is identical).
- Screens are drawn with fills (`Panels`), no GUI textures.
- Case proportions (thinned twice after review): base 3 px (vending: coin slit and stock light) / 2 px (display), glass up to the 1 px frame at 15-16 px. `VendingBlock.BASE_HEIGHT` / `DisplayBlock.BASE_HEIGHT` drive the shapes, the facade height and the item's height (middle of the glass); `tools/assets.py` has the same numbers.
- Both cases are glass on top too: a 2 px metal frame holds a flat glass pane one pixel below its top (the pane has an up and a down face, so it shows through the walls). Walls and top use `tradery:block/case_glass` (faint tint + streaks) instead of vanilla glass, which is almost fully transparent and made the top look open.

## 2026-09-30: Quick trade and look-at hint
- Researched the predecessors' code (original Vending Block 1.6.4–1.12.2, Restocked): no-GUI trading by clicks, and an own look-at box at the top of the screen (not a WAILA plugin). Holding right-click repeats only through vanilla's 4-tick use repeat.
- The author's call: sneak + use buys, sneak + attack sells (buyback blocks), holding repeats; a plain use still opens the buyer window. The owner's sneak + click stays vanilla (so the owner can still break the block).
- Client side: the click is taken before vanilla acts (Fabric `UseBlockCallback` returning FAIL on the client, `ClientPreAttackCallback`; NeoForge `InputEvent.InteractionKeyMappingTriggered`), so a held block isn't placed and nothing is mined. Attack fires every tick and use every 4 ticks while held; `QuickTradeInput` sends at most one `VendingQuickTradePayload` per 4 ticks. On NeoForge the `RightClickBlock`/`LeftClickBlock` events weren't enough: a cancelled use still sends the vanilla packet, and a survival attack only fires once.
- Server: reach (`isWithinBlockInteractionRange(pos, 1.0)`), loaded chunk, the block entity, the trade rate limit (10/s), then `VendingTrades.execute(…, 1)`. The action bar adds up a streak (same block, same direction, ≤ 30 ticks apart): "Bought 20 × Bread for (coin)12.50". Sounds: experience-orb ding for a trade, dispenser click for a refusal (vanilla sounds, no new assets).
- Hint layout (reworked after review: the first version was too wide and mixed alignments): a vanilla tooltip card (`TooltipRenderUtil.extractTooltipBackground`), everything centered: owner, "Sells [icon] for [price]" with counts drawn on the icons and no item names, then the keys. Names and item tooltips only while sneaking. Keys use short names for the usual bindings ("Shift", "RMB"/"ПКМ"), the game's name otherwise; the "RMB: window" part was dropped.
- Hint: rows cached per target (position, settings object, admin flags, owner, STOCKED, sneaking, currency) and rebuilt only on change. "Sold out" comes from the STOCKED block state; the buyback-side reasons (owner broke, block full) are only known on the server and show when you try.

## 2026-09-30: Money sources
- Coin ore payout lives in `CoinOreBlock#getDrops`: players, explosions and machines all come through it, so no path skips the rules. The loot table decides the coin count (data packs can add Fortune); the block decides where the money goes.
- Coin ore textures are overlays on vanilla `block/stone` / `block/deepslate` (two coplanar elements, like grass block sides): no vanilla pixels are copied into the mod.
- Coins are money in the world: withdrawals and coins minted by non-player mining add to "cash in the world", deposits subtract (stats, inflation damping).
- `ore.dailyCap` limits direct mining; coins dropped by explosions/machines aren't capped (they need automation or TNT). Known and accepted.
- Rewards hook through common mixins (craft: `ResultSlot`, fish: `FishingHook#retrieve`, advancement: `PlayerAdvancements#award`, spawner tag: `EntityType#loadEntityRecursive`, placed marks: `BlockItem#placeBlock`, coin pickup: `ItemEntity#playerTouch`) and loader events for kills and block breaks. A GameTest loads every mixin target.
- `rewards.json5` sections are `{ enabled, rewards: { key: {min, max, chance} } }` instead of the spec's flat map: each type can be switched off without deleting its entries. `max` defaults to `min`, `chance` to 1.
- Blocks moved by pistons lose their "placed" mark (the mark is per position). `mine` rewards are off by default and the config comment says so.
- Server config and rewards config have test-only setters used by GameTests, restored in `finally`.

## 2026-10-06: Release checks, automated
- The manual checklist became runnable checks. NeoForge has no client test framework, so a dev-only test mod (`neoforge/src/clientTest`, mod id `tradery_client_test`) drives a real client: creates a flat world through the Create World screen, holds the real key mappings through the normal tick (the mouse is grabbed first: vanilla only continues an attack with a grabbed mouse), checks items and money on the integrated server, takes screenshots, quits; a failure halts with exit code 1. MDG loads every mod of `mods {}` into every run by default, so the standard runs list only `tradery`.
- Fabric: `NetworkClientTest` uses the client GameTest dedicated server, so all payloads and the block entity sync go through their codecs (singleplayer skips serialization); Bob, a `FakePlayer` that joined the economy, is the second player. `PerformanceClientTest` measures `MinecraftServer#getAverageTickTimeNanos` and `Minecraft#getFrameTimeNs` (the test client draws once per tick, so wall time per frame only shows the 50 ms tick).
- **Found: trades were saved apart from their chunk.** Minecraft 26.3 writes a changed chunk on its own ~10 s after the change (`ChunkMap#saveChunksEagerly`), but server saved data and player data only at the autosave (5 min) or on stop. After a crash the stock was newer than the money (the first `kill -9` run: stock after the trades, balances before) — a buyback could duplicate goods, a sale lose them. Fix: `TradePersistence` remembers which players traded at which chunk; a mixin on `ChunkMap#save(ChunkAccess)` (every chunk write: eager, unload, autosave) then calls `SavedDataStorage#scheduleSave` (snapshots all dirty server data in that tick) and `PlayerList#save` for those players (invoker mixin). Verified with `tools/crash-test.sh` (real `kill -9` of a dedicated server, then a second launch checks one consistent state) and a negative control: without the hook the same run fails with a mixed state.
- **Found: NeoForge showed a "Mods loaded with 1 warning" screen** before the title screen: `logoFile` is deprecated in NeoForge 26.3. `neoforge.mods.toml` uses `iconFile` (the icon is square).
- The wrong-button message (sneak + attack on a selling block and vice versa) is now the client's own, with the hint's short key names, and no request is sent; the server keeps its check and message for other clients.
- Create and Mekanism have no 26.3 builds (Modrinth, 2026-10-06: latest 1.21.1). `coin_ore_not_processable` asserts what their machines rely on: coin ore blocks/items are in no `c:ores`/`raw_materials`/`dusts`/`ingots`/`nuggets` tag, no smelting or blasting recipe takes ore or coins.
- `ore_feature_places_ore` tries the vein up to 10 times: a random blob in a 5x5x5 stone cube can miss it.

## 2026-10-09: Economy lifecycle order
- Found while porting to 1.20.1 (the Forge crash-test mod used the API in its own `ServerStartedEvent` listener and sometimes ran first): the economy starts on the server-started event, so an addon calling `TraderyEconomy` in the same event could see "economy is not available", depending on the mod order. Now the economy starts before other listeners (NeoForge `EventPriority.HIGHEST`; Fabric: event phase `tradery:economy` ordered before `Event.DEFAULT_PHASE`) and stops after them on server stopped (`LOWEST` / a phase after the default one). Same on every version branch.

## 2026-10-18: v1.1 Living Market (design)
- Asked for on Reddit ("would be cooler if villagers could buy from your shops... if villagers wandered up"). Researched the niche: Lightman's Villager Tycoon (spawns new villagers near machines, 0–5 stars, Forge 1.20.1 only), Village Business (emeralds, Fabric 1.20.x, abandoned), Customers (spawner blocks and timed "shifts", a shop minigame). None models a village economy: buyers come from nowhere and money is unlimited.
- Tradery's take (author's choice): the villagers that already live in the village are the customers; they pay Tradery currency from wallets that refill daily by profession level (so levelling villagers by trading makes them richer customers), want items by profession (data pack), respond to price against a fair price (data pack), saturate a village's demand per item, and remember the owner through vanilla gossip (fair prices = TRADING gossip, gouging = MINOR_NEGATIVE), which also gives vanilla trade discounts.
- (Superseded the same day, see "villager trading for money" below.) Vanilla villager trading stays on emeralds (trading halls, trade data packs and other mods keep working); currency and emeralds are linked by the changer stall at the village market. Villagers selling raw goods to buyback blocks: not in 1.1 (author: undecided).
- Money minted by villagers is limited by the wallet, a per-village daily cap and the shared inflation damping; only villagers with a bed and a job site shop by default (caged trading-hall villagers can't walk to a stall anyway); only loaded chunks, no catch-up simulation.
- No villager AI mixins: a server-side customer manager drives the vanilla WALK_TARGET/LOOK_TARGET memories, so the code stays the same across loaders and ports. Wallets live in Tradery saved data, not on the entity (one implementation for Fabric, NeoForge and the 1.20.1 Forge port).
- Village market: a stall structure added to the five village house pools (weight from config), server-owned infinite vendors that burn payment (a sink for single-player money), offers rolled at generation by a structure processor from data-pack tables.

## 2026-10-18: v1.1 Living Market (built)
- Two parallel areas: villager customers (package `village`: manager, purchases, ledger saved data `tradery:villagers`, needs/prices data packs) and the village market (package `market`: stall templates for five village types plus a changer stall, processor `tradery:market_stock`, pool injection on server start through a `StructureTemplatePool` accessor). Details of each call are in the notes of that change: one customer per stall at a time, only if the block in front of it is free; a new wallet starts with one day's wage; wages per whole in-game day, capped at `walletDays`; reputation factor `2^clamp(rep / 25, -1, 1)`; TRADING +2 per lot at r <= 1, MINOR_NEGATIVE +2 per visit at r >= `gougingRatio`; market offers rolled in the smallest unit the table writes; the changer's buy price is capped at its sell price (else buy + sell back mints money); `exploration_map` offers are rejected (they search structures during world generation); zombie villages get no market; `market.*` applies after a restart.
- **Found in a live world: the default wages were too low.** In a freshly generated village almost every villager is a novice; with 1.00 per day a novice couldn't afford a 2-bread lot at the fair price (1.20), so nobody came for days. Wages are now none 1, novice 3, apprentice 5, journeyman 8, expert 12, master 18 per in-game day: a village of 10–15 novices spends about 30–50 a day at fair prices, about what a coin ore trip pays; `dailyCapPerVillage` (200) still bounds big villages.
- Customers are found through the vending index (`VendorsData`), which player placement fills (`VendingBlock#setPlacedBy`) and loading self-heals; a block set up by code must be added to it (the shots test does).
- `tools/structures.py` wrote the palette key `Name`; 26.3 reads `id` (`NbtUtils.readBlockState`). The GameTest template only worked because unknown blocks become air; fixed.
- Live check (`LivingMarketShotsClientTest`, only with `TRADERY_MARKET_SHOTS=1`): a normal world, a plains village with generated market stalls, a player's bread stall next to it; the village's farmer walked over and bought ("Farmer bought 4 × Bread for 2.36"), the owner got the notification and the HUD popup, the owner screen shows the villager toggle.

## 2026-10-18: v1.1 villager trading for money
- Author's choice after the first 1.1 build ("Валюта вместо изумрудов"): the villager trade window works in money. Every emerald in a villager's offers is worth `villagerTrading.emeraldValue` (default 3, the changer's selling price): emeralds the player pays come off the balance into the villager's wallet; emeralds the villager pays come out of its wallet, so an empty wallet means "come back tomorrow". Emeralds stay an item (changer, wandering trader, other mods). `villagerTrading.enabled: false` gives the vanilla window back.
- Tradery's own window instead of patching vanilla's: vanilla's `MerchantMenu`/`MerchantScreen` are built around emerald item slots; replacing them client and server side is fragile and differs on 1.20.1/1.21.1. One common mixin on `Villager#startTrading` (HEAD, cancellable; after vanilla's checks for babies, sleep, empty offers and the stat) applies vanilla's special prices (`updateSpecialPrices`, reputation and Hero of the Village) and opens `VillagerTradeMenu`. No item slots, like the vending buyer menu; a trade is a menu button click (`offer * 2 + all`).
- One trade = one ledger transaction of the net amount (pay to `tradery:server` / mint from it, `tradery:villager/trade`), done after checking items, balance and wallet and before taking the items, so a refused transaction (ceiling, API event, locked account) changes nothing. Item costs match vanilla's `ItemCost#test`, plain stacks first. Vanilla's `notifyTrade` does uses, experience, level-ups, gossip and the advancement trigger.
- Money paid to a villager goes into its wallet without the `walletDays` cap: villagers spend what players pay them at players' stalls.
- Wandering traders keep emeralds (no wallet, they don't belong to a village).
- Crash safety: villager trades change a player's inventory and saved data but no chunk. `TradePersistence` now also saves players with villager trades whenever it saves the economy data for a chunk, and schedules the economy data save when such a player leaves (vanilla saves the player then).
- `AbstractVillager#overrideOffers` is a client no-op on the server; tests replace the live `getOffers()` list.
- **Found in the live check: the client didn't see the inventory change while the window was open** ("You have 0 × Raw Rabbit" with 64 in the hotbar). Vanilla syncs inventory slots only through the open menu, and this menu has none. `VillagerTradeMenu#broadcastChanges` also broadcasts the player's inventory menu; the client applies container-0 slot updates whatever screen is open (`ClientPacketListener#handleContainerSetSlot`).

## 2026-10-19: facade cut, not squeezed
- Author's review: the material of the vending base looked flattened. The facade was the whole block model scaled to the 3 px base, so a 16 px texture showed in 3 px (planks became thin stripes). Now `FacadeSlicer` cuts the model at the base height like a slab: side faces keep the bottom rows of their texture at full scale, the top face comes down to the cut; a face the cut can't follow falls back to the old squeeze.
- The parts come straight from `ModelManager#getBlockStateModelSet` (vanilla's `collectParts`, seed 42) and are submitted with `submitBlockModel`; tints and the block's own light come from `BlockModelResolver` once. Not through `BlockModelRenderState#setupModel`: on Fabric the renderer API overwrites `BlockStateModelWrapper#update` and fills a mesh instead of parts (the first try drew a full-height block there). Cut parts are cached per block state for the renderer's life.

## 2026-10-20: village economy (design, in 1.1)
- Author's choice after the 1.1 build: the board with orders, villager suppliers, village prosperity, server conveniences (shop ledger, multi-offer counter), plus treasury and projects, trade between villages with caravans, market days with rented trading places, and raids hurting the economy. All in 1.1, then the ports.
- Researched the niche: bounty boards (Village Bounties, Villages Plus, Bailey's Dailies), village growth (Sovereign, Pueblo Vivo), market days (Mercantile). None ties them to money. Tradery's angle: every order, supply, tax and project is a real money flow from villagers' wallets and the village treasury, visible in `/eco stats`.
- A village is its bell (POI `meeting`), keyed like the customers' villages (`bell:<dim>:x,y,z`), so demand, wallets and the new state line up. Its state is a separate saved data `tradery_villages` (`VillageEconomy`/`VillageState`); daily changes (prosperity decay, treasury income) are applied lazily on the next touch, nothing runs for unloaded villages. A census of loaded villagers every 600 ticks gives population, employed, professions and the village type.
- Prosperity comes from money flows (purchases ×1, window trades ×0.5, orders ×1, supplies ×0.5, projects ×0.5 per major unit), decays 5% a day, and sets the level (Hamlet / Village / Town / Trade city at 0 / 300 / 1500 / 5000). Levels scale wages and treasury income, orders, market days, the villages' spending cap and rent.
- The treasury is a counter like the wallets: income per villager per day up to 7 days, plus rent and a 10% tax on what players pay villagers in the trade window (taken from the villager's share, so no money is created). Rewards paid from it are minted from `tradery:server`; projects and rent paid into it are burned, the main new money sink.
- Config: one `villages` section with subsections (levels lists, orders, suppliers, caravans, marketDay, rent, threats): `ServerConfig` was at 10 of Mojang's 16 codec fields and `villagers` at 16.
- Built in parallel by three areas (board/orders/projects, suppliers, commerce/caravans/raids) on a core the coordinator wrote first (`Villages`, `VillageProjects`, the `VillageCommerce` API stub), with a brief and file ownership, as in the first 1.1 round.

## 2026-10-20: village board, orders, projects (built)
- The board has no block entity: its village is the nearest bell within `villages.boardRadius`. Boards on generated market stalls carry `market=true` and break only for an admin with the vendor key, like the market's vending blocks.
- Orders are topped up to the level's count once a day when the board is first opened (restoration orders come on top while `restorationDue`); each order's whole reward is reserved from the treasury when posted and returned when it expires. Items: the wants of the village's professions (`any` for the jobless) plus its dear goods, weighed like everyone wanting them; 8–64 per order, sized to an equal share of the treasury. Delivery takes plain stacks only, partial or full: checks, then the reward minted from `tradery:server` (`tradery:village/order`), then the items; +2 `TRADING` gossip per started 8 items at villagers within 32 blocks of the bell; the board shows their average as the viewer's reputation.
- Projects (`tradery:village/project`, burned): once per village, from the required level; the golem's room or the stall's flat free spot (heightmap ground, paths and farmland don't count, facing the bell when it can, within 24 blocks) is found before charging. The stall is placed like world generation with offers rolled.
- Bell hint: the client asks while looking at a bell (every 2 s), the server answers at most every 10 ticks per player and never creates a village for a look.
- Test spaces are roofed with barriers at a height that differs between the loaders' test structures (Fabric: 8 above the floor); tests that search the ground by heightmap clear any barrier above their area.
- Live check: generated plains village made a Town, 34 packed ice delivered for 74.12, the three tabs. Found: cut text without an ellipsis (descriptions, caravan news) and "in 1 days"; fixed (ellipsis + tooltip, "tomorrow" keys in 15 languages).

## 2026-10-20: villager suppliers (built)
- Production per profession from `tradery/villager_supplies` (all 13 working professions), novice `per_day`, +25% per level above, rounded; stock piles up lazily to `suppliers.stockDays`, starts with one day, lives next to the wallet in `VillagerLedger` and goes with it; goods of another profession are dropped when the profession changes.
- The same customer manager sends suppliers: only to BUYBACK money blocks with the villagers flag, only villagers that produce the goods and have a lot in stock, at a price ≥ ⌈fair × the village's regional factor × `minPriceRatio`⌉ (BigDecimal), with room in the stock and the owner able to pay one lot. Visit chance and radius use `VillageCommerce.visitFactor/radiusFactor` for customers and suppliers; the projects' `visitChance` only for customers. A licence widens the radius only for villagers of that village.
- `VendingTrades.buyFromVillager`: owner pays the full price to `tradery:server` (`tradery:villager/supply`), the fee burns, the villager's wallet gets the rest (no cap), items come from its stock; prosperity `points(received, 0.5)`; notifications and offline summary have their own counters. Plain stacks only; a later data file overrides the amount for the same item, `per_day: 0` removes it. The villagers flag is on by default, so existing buyback blocks get suppliers too (SPEC: "the same flag").

## 2026-10-20: village commerce (built)
- Regional prices from `tradery/village_types/<type>.json` for all seven villager types (plains keeps bread and suppliers' produce at ×1); `prices/regional.json` adds fair prices for sand, cactus, terracotta, logs, ice and the like so caravans can value them.
- Market days: interval by level minus projects, at least 1; a village's first market day falls on its own day within the first interval (key hash) so neighbours differ; re-planned when the clock is set back. Visits ×`visitMultiplier`, the villages' spending cap ×2; players within 64 blocks of the bell are told once a day per village.
- Rent: one transaction player → server account, the amount goes to the treasury; renewing only when less than one rent period is left (no double click), no prosperity for rent.
- Caravans: a village of level ≥ `minLevel` sends one every interval (minus `caravanDaysLess`) to a random known village of another type in the same dimension within `maxDistance`; purse = min(treasury, daily income × interval). It arrives on the destination's market day if that comes before the next caravan, else at once, when the bell is loaded, in daylight, with no raid: a vanilla wandering trader tagged `tradery_caravan`, named "Caravan from …", two leashed llamas, `despawnDelay = stayTicks`. Its offers are vanilla `MerchantOffer`s with a placeholder emerald on the money side; the real amounts live in `tradery_caravans` and go to the trade window, which is shared with villagers (`Partner`: the wallet or the caravan's purse). It sells the origin's cheap goods at the origin's prices and buys the destination's dear goods at local prices, never buying back what it sells; purchases burn into the purse, payouts come from it; the purse returns to the origin's treasury when the trader leaves or dies. Ordinary wandering traders stay on emeralds; a tagged trader without a live caravan record refuses.
- Raids at loaded bells are checked every 20 ticks with `getRaidAt`; an outcome counts once and only if the raid was seen running. Lost: prosperity ×(1 − 0.3 × raidLoss), treasury and loaded villagers' wallets −50% × raidLoss; won: +`raidWinProsperity`, restoration for 3 days, players nearby told.
- Constants from SPEC kept in code, not config: licence radius ×1.5, market-day cap ×2, raid losses 50%, restoration 3 days, 2 llamas.

Not a `Container`, so hoppers can't reach it.

Stand position: the block on the buyers' side, same `HORIZONTAL_FACING` property as vending blocks.

## 2026-10-23: review round (performance, robustness, client)
Three read-only reviews (server performance, correctness/exploits, client/code quality) over the whole 26.3 code; what was confirmed by tracing got fixed, GameTests Fabric 106/106, NeoForge 104/104, JUnit green.
- **Saves coalesced.** `TradePersistence.chunkSaved` used to call `scheduleSave()` (encodes every dirty saved data on the server thread) and save each trader for every chunk written with trades, up to 20 chunks a tick every ~10 s; now it only marks, and `flush` at the end of the level tick does one server-data save and one save per trader. Same tick, so the crash guarantee (chunk, money and inventories written together) holds. The census marks `VillageEconomy` dirty only when a count changed, so a save between trades encodes nothing of it.
- **Customer scan spread out.** All stalls were scanned in one tick every `checkIntervalTicks`, each with a 48-block POI search for its bell; now each stall has its own tick in the interval (from its position) and the bell is cached for 1200 ticks (`VillagerCustomers.BELLS`). A villager's `LOOK_TARGET` is set once per visit, not every tick.
- Caravans: a village with no destination in reach retries tomorrow, not every 100 ticks over all villages. Orders: the priced items are found once per data pack load (`VillagerMarket.generation`), not by walking the whole item registry at every board opening. Stall spots: ring offsets built once per radius; funding limited to one per 20 ticks per player (`VillageBoard.allowFund`). Crafted stacks pay one reward transaction (rolled per item) instead of one per item. The transaction log's queue is bounded (10 000 lines, drops counted and reported). Per-player rate-limit maps are cleared on server stop.
- **Client render paths allocate nothing per frame** (AGENTS rule): HUD popups are formatted and measured when added, hint rows measured in `layout`, the showcase item state takes the live stack (no `copyWithCount`), the animation override is a field not `valueOf`, the "you have" counts of the board and the trade window are counted on the tick (`containerTick`), not on every frame.
- **Untrusted samples.** `GhostSamplePayload` decoded item stacks with the trusted codec; a survival client could send any component patch (up to the 32 KB packet cap) that then lived in the block, the save and every chunk viewer's update packets. Now `OPTIONAL_UNTRUSTED_STREAM_CODEC`, the trade rate limit on the payload and on the owner's Save, and `GhostSlots.acceptableSample`: a sample's component patch must encode to ≤ 2 KB of NBT (`MAX_SAMPLE_BYTES`), through the same check for the owner's own clicks. Saving unchanged settings sends nothing.
- **Pruning keeps what players paid for.** Villages unseen for 60 days were dropped by raw clock delta (`/time add`, long absence), with funded projects, treasury, open orders and licences; now a village with any of those is never pruned. Settings codecs are lenient on the goods and price-item fields: a removed mod's item loses the sample, not the price, mode and flags (and not all six counter offers).
- **Wallet vs. tax.** The trade window admitted a trade when `payout − price ≤ wallet`, but the village keeps its 10% tax of the payment, so a villager could be charged up to the tax more than it had (clamped to 0, treasury still credited). The check now uses what the partner keeps (`Partner.keeps`).
- Known and left: `ItemEntityMixin` at HEAD runs before NeoForge's pickup event (claim mods can't veto coin deposits); `Order`/`Caravan` codecs have required fields (a renamed field would drop the record on load); Fabric's `@GameTest` default is 20 ticks against NeoForge's 200 (two long tests set `maxTicks` explicitly); the API events' constructors lack Javadoc/`@ApiStatus.Internal` and the 1.1 `Reasons` lack `@since`; the three notifier paths and the two `sellToVillager`s still duplicate ~40 lines each.
- **Port hazard (1.21.1 / 1.20.1 only):** there `/time set day` resets the absolute day time, which would pin `today()` and fire the "clock set back" branches every day (no wages, no produce, orders churn). In 26.3 the marker clock only moves forward (verified in `/time`'s `resolveTimeToMoveTo`). The ports need a day counter that only advances.

## 2026-10-23: treasury donations and history (built)
The author asked what the treasury looks like and took both offers: a direct donation and a week of history on the board.
- **Donation as the first "project".** The projects list on the Village tab starts with "Donation to the treasury": an amount box under the list and the Fund button turning into "Donate X". It is its own payload (`VillageDonatePayload`, the amount can't ride on a button id) handled by `VillageBoardMenu.donate` with the same checks as a click (open valid menu, reach, `VendingTrades.allow`). `VillageFunding.donate` burns the money (`Reasons.VILLAGE_DONATION`, player → server account) and puts it in the treasury above the income cap, with prosperity and gossip as for a project of that cost. Donations flow back out as order rewards, which the board sizes by the treasury, so the money is conserved; no cap on the amount.
- **History recorded where the treasury changes.** `VillageState.history` holds up to 7 `DayFlow(day, in, out)`; `Villages.recordFlow` is called in `touch` (income actually applied under the cap), `addToTreasury`, `takeFromTreasury` and `loseTreasury`, so no call site can forget it. Money coming back (expired orders, a caravan's purse) counts as "in", reservations as "out": the chart is cash flow, not profit. A day before the latest entry (the clock set back) folds into the latest. `Villages.set` writes nothing (tests and admin). Sent in `Info.history` (list bound 7), drawn as two bars a day without per-frame allocation; the tooltip lists the days and the week's totals.
- GameTests `board_donation` and `board_treasury_history`; Fabric glue 105 wired.
- **Found on the way: left clicks on the board's tabs and rows and on the trade window's rows checked `event.button() == 0` (GLFW's left button). 26.3 numbers mouse buttons the SDL way: `InputConstants.MOUSE_BUTTON_LEFT` is 1, right is 3, and `AbstractWidget.isValidClickButton` wants 1. ## 2026-10-24: placement like village houses, level buildings, festivals (built)
The author's first in-game test: the market stall stood on the workshop's roof. `findSpot` took the heightmap's top as ground, and a roof is a flat sturdy top.
- **Placement rules** (vanilla does this at worldgen with jigsaw projection and `beard_thin` terrain adaptation; after worldgen nothing adapts the terrain, so the spot must be right as it is): real ground = three solid dry blocks down from the top (`GROUND_DEPTH`; a roof or an awning has air underneath); no column of the footprint inside a village structure piece taller than a street (`StructureManager.getStructureWithPieceAt` with `StructureTags.VILLAGE`, pieces of `getYSpan() > 2`: houses, huts, not the flat street pieces); beside a dirt path first (`besideStreet`), then anywhere; lamp posts also need the open sky (the motion-blocking heightmap at the post). Sources: the Bedrock structure feature's "grounded"/"unburied" constraints and the Terrain Place mod's note that the generator's heightmap is wrong after the fact both point the same way: read the loaded world, not the generator.
- **The village builds for itself** (`VillageBuildings`): a `savings` fund inside `VillageState.Growth` (with `buildings`, `buildDay`, `festivalDay`; a nested record because `RecordCodecBuilder.group` stops at 16 fields), fed by `savingsShare` of the daily income in `touch` while `next(village)` is pending; orders, caravans and raids never see it. `tryBuild` once a day per village from `onLevelTick` every 200 ticks for loaded bells, through `findSpot`/`place` (the trade hall with the market processor, so its vendors get offers); signs in the template get the village's name (`nameSigns`, waxed). Costs 200 / 600 / 1500: a Village of ten villagers at ×1.25 wages saves ~6 a day, so the well takes a month; donations don't feed the fund (they are for orders, as the author asked) — a lever for later if that proves slow.
- **Festival** (`VillageFestivals`): due = market day, level ≥ `minLevel`, dusk by the overworld clock (`getOverworldClockTime() % 24000` in 9000..12000, the villagers' meeting hours), not held today. Start rings the bell (`BellBlock.attemptToRing`), tops wallets up by `walletBonusDays` of wages (`VillagerPurchases.dailyWage`), +25 prosperity, `VillageTitlePayload(festival = true)` and a chat line to players within 64; one rocket every 100 ticks near the bell until 12000. No trade discount: the trade window's math stays untouched; the wallet bonus is the money-mod way to celebrate.
- GameTests `buildings_savings_from_income`, `buildings_built_from_savings`, `festival_on_market_day`; Fabric glue 110 wired.
- **Streets.** The author asked whether streets could be upgraded and whether vanilla's uneven streets could be evened out. Vanilla streets are `terrain_matching` jigsaw pieces: they are bent onto the terrain on purpose, with a processor that puts planks where a path crosses water and leaves 10–20 % grass; mods that make nicer roads (RoadWeaver, RoadArchitect) generate their own with A* under slope limits and don't touch village pieces either. Tradery stays post-generation: `VillageStreets.connect` lays a one-bend path from every new building to the nearest street within 12 blocks (natural ground only, a block up or down at most), and the "Paved Streets" project (`Action.PAVE_STREETS`) turns the dirt paths within the board radius into the type's pavement and fills one-block dips. Worldgen is left alone: changing it would change every village of every world, with or without the mod's economy.
- The board's "Saving for…" line is two lines (name, then the plain numbers): with the coin glyph and both amounts it didn't fit the column, and the 8-px coin reads as a smudge next to small text.
- GameTests `board_project_paved_streets`, `streets_connect_building`; Fabric glue 112 wired.
- **Street lights** (the author: lamps didn't reach every street, make them nicer). Building guides agree on a slim post in the settlement's materials, the light hanging from an arm over the road, the height matched to the houses and spacing tight enough to leave no dark spots. `VillageLamps`: candidates are the ground blocks beside every open street block of the village (same `scanBox` as paving), nearest the bell first; a lamp needs real ground under the open sky outside houses, five free blocks for the post, the street clear five blocks up (three under the lantern: golems are 2.7 tall), no door beside it, nobody there; streets with block light ≥ 10 are skipped (vanilla lamp posts, torches, earlier lamps), lamps 10 apart, 48 at most. Style per type: wall base, fence pole (desert: sandstone wall), arm, hanging lantern; fences and walls get their connections from `Block.updateFromNeighbourShapes` after the whole lamp is placed. A village without streets keeps the old plain posts around the bell (at most 8). Daily pass for lit villages, like paving. The test waits for the light engine (`succeedWhen`) before checking that a lit street needs no lamp.
- **After the author's second test** (paving left whole streets dirt; the watch post built nothing): paving scanned 48 blocks around the bell, villages reach further. It now scans the village structure's box (`StructureManager.getStructureWithPieceAt(bell, StructureTags.VILLAGE)`, inflated by 4, at least the board radius), never loads a chunk (`hasChunkAt` before the heightmap, neighbours read as air when unloaded), fills one-block grass gaps between open streets (the 10–20 % vanilla's street processor turns back to grass), and repaves once a day per paved village with a loaded bell (in-memory day map) for chunks loaded later. Projects take `structure` alongside any action; the watch post builds `watch_post` (a 3×6×3 lookout) and its golem is moved next to it (`golemSpot` around the post) when there's room.

## API notes (26.3)
- `ResourceLocation` → `Identifier`; `Identifier.read(String)` returns `DataResult`.
- `SavedDataType(Identifier, Supplier, Codec, DataFixTypes)`; `MinecraftServer#getDataStorage()`.
- Permissions: `Commands.LEVEL_*` are `PermissionCheck`s; `PermissionLevel` enum; `ServerPlayer#permissions()`.
- GUI: `GuiGraphicsExtractor` (`text`, `fill`, `blitSprite(RenderPipelines.GUI_TEXTURED, …)`, `pose()` is a `Matrix3x2fStack`); the open screen is `Minecraft#gui.screen()`; F1 is `gui.hud.isHidden()`.
- `InputConstants.Type.KEYBOARD` (not `KEYSYM`); `KeyMapping.Category.register(Identifier)`.
- Mouse buttons are SDL-numbered: `InputConstants.MOUSE_BUTTON_LEFT` = 1, `MIDDLE` = 2, `RIGHT` = 3 (never compare with 0); Fabric's client GameTest `TestInput.pressMouse` takes the same numbers.
- `Player#sendOverlayMessage(Component)` for the action bar.
- `GameTestHelper#makeMockServerPlayerInLevel()` is deprecated for removal in 26.3 (still works).
- Worldgen: configured features in `data/<ns>/worldgen/feature/`; loot table functions are `"modifier"`.
- `PushReaction.IMMOVEABLE` (no `BLOCK`); entity type constants in `EntityTypes`; `PoseStack#rotateDegrees(Axis, float)`.
- `CreativeModeTab.Output` is protected in vanilla: `:common` gets it through `META-INF/accesstransformer.cfg` (both loaders open it anyway).
- BER: `extractRenderState(be, state, partialTicks, cameraPos, crumbling)` + `submit(state, pose, collector, camera)`; items via `ItemModelResolver.updateForTopItem`, blocks via `BlockModelResolver.update`.
- Screens: `extractBackground` / `extractLabels`; the open screen is `Minecraft#gui.screen()`; `Minecraft#hasShiftDown()`.
- Block models: texture refs can be `{"sprite": ..., "force_translucent": true}`; elements support `light_emission`.
